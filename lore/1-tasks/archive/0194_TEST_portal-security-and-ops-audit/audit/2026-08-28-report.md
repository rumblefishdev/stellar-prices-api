`cdk deploy` and every other control-plane caller in the account — which also
hosts the `Explorer-production-*` stacks. Against the observed peak of 12/s
(a deploy plus local runs) there is no headroom at the ceiling and a great
deal below it: a portal gated behind Stellar Discord membership will not see
2.5 loads/s.

Recommendation, in [[0190]]'s order and before any storage: (1) de-duplicate the
shared `GetApiKeys` — the two routes each run `list_named` for the same user in
the same load — cold 4 → 3; (2) give the reveal the same in-process cache the
usage route has — warm 2 → 0. Both are handler changes with no IAM or
infrastructure component. Neither gates the flip. **PASS** as "known and
bounded".

## Recommendation

**NO-GO** for `PORTAL_ENABLED='true'` today.

Not because the assembled infrastructure is wrong — the twelve checks find the
gateway, CloudFront, IAM and bucket composition exactly as the slices intended,
byte-identical between `develop` head and production — but because two
operator steps the runbook has always listed were never run, and the flag's own
failure mode makes that decisive: with the secret and the parameters absent,
`PORTAL_ENABLED=true` fails Lambda init and takes **`/v1` down with the portal**
(runbook §5; `config.rs:146-148`; `eligibility.rs:135`).

Order to reach GO: B1, B2, B3, then re-run E9 and E10 from this file (two
commands each), then flip. The flip is the one-word diff
`PORTAL_ENABLED: 'false'` → `'true'` in `compute-stack.ts` plus
`make -C infra deploy-production-compute`, and it is **reversible by the same
one-word diff plus the same deploy** — no state is created by opening that
closing does not simply stop serving. After the flip, close E1 and E2's
BLOCKED halves with the curls given there, then hand to [[0164]].
