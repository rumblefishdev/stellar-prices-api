# Dashboard access on request — through IAM Identity Center

An alternative to [0295-dashboard-access-on-request.md](0295-dashboard-access-on-request.md),
which creates an IAM user in the production account. Same request, same review
window, same removal. The difference is where the identity lives: here it is a
user in Rumble Fish's IAM Identity Center, and the production account only
holds a role while the assignment exists.

> **Not walked.** Written 2026-09-29 from the AWS CLI reference. Nothing below
> has been run against the organization yet. The first operator to use it
> records the walk in task 0294's history and fixes what did not match.

## Who runs this: the organization administrator

Not the prices operator with `soroban-admin`. IAM Identity Center is managed
from the organization's management account only. The production account can
see the instance but cannot change it.

Every step except the checks in §5 needs an administrator role in the
management account: the **Rumble Fish AWS organization administrator's**. The
change adds an outside person to Rumble Fish's company directory and a
permission set to the organization, so the organization administrator runs it,
or agrees to it before anyone else with that role does. How to reach them is
not recorded in this repository; ask in the team channel.

## Why this path

- No IAM user, no password generated by the operator, and no policy written
  outside CDK in the production account.
- MFA is enforced by Identity Center at sign-in (§3), not by a policy
  condition.
- The reviewer gets temporary credentials through the Rumble Fish AWS access
  portal.
- The assignment provisions a role `AWSReservedSSO_PricesDashboardRead_<suffix>`
  in 750702271865 for as long as it exists. That is the "read-only IAM role" AC 8
  names, bounded by the review window.

The costs: every request needs the management-account admin role, and the
reviewer is a user in Rumble Fish's company directory until §6 removes them.

## 1. The request

Same as §1 of the IAM runbook: a named person (first name, surname), their own
e-mail, the purpose and an end date. Record the request in the task history
before creating anything.

## 2. Once: the permission set

Created once and kept. Without an assignment it provisions nothing in the
production account.

```bash
export AWS_PROFILE=<management-account admin profile> AWS_REGION=<Identity Center region>
[ "$(aws sts get-caller-identity --query Account --output text)" = \
  "$(aws organizations describe-organization --query Organization.MasterAccountId --output text)" ] \
  || echo "not the management account — stop"
INSTANCE=$(aws sso-admin list-instances --query 'Instances[0].InstanceArn' --output text)
STORE=$(aws sso-admin list-instances --query 'Instances[0].IdentityStoreId' --output text)
PS=$(aws sso-admin create-permission-set --instance-arn "$INSTANCE" \
  --name PricesDashboardRead \
  --description "prices-api production: read-only CloudWatch dashboards, metrics and alarms" \
  --session-duration PT4H \
  --query 'PermissionSet.PermissionSetArn' --output text)
aws sso-admin put-inline-policy-to-permission-set --instance-arn "$INSTANCE" \
  --permission-set-arn "$PS" --inline-policy file://dashboard-read-sso.json
```

`dashboard-read-sso.json` is the first statement of the IAM runbook's policy,
without its MFA condition and without the self-service statements:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadDashboardsMetricsAndAlarms",
      "Effect": "Allow",
      "Action": [
        "cloudwatch:GetDashboard",
        "cloudwatch:ListDashboards",
        "cloudwatch:GetMetricData",
        "cloudwatch:GetMetricStatistics",
        "cloudwatch:ListMetrics",
        "cloudwatch:GetMetricWidgetImage",
        "cloudwatch:DescribeAlarms",
        "cloudwatch:DescribeAlarmHistory",
        "cloudwatch:DescribeAlarmsForMetric"
      ],
      "Resource": "*"
    }
  ]
}
```

Why the condition goes: `aws:MultiFactorAuthPresent` is not present in a role
session federated through Identity Center, so `"Bool": {"aws:MultiFactorAuthPresent": "true"}`
would deny every action. The self-service statements go because the reviewer
enrols MFA and sets a password in Identity Center, not in IAM.

In a later run, find the permission set by name:

```bash
PS=$(for p in $(aws sso-admin list-permission-sets --instance-arn "$INSTANCE" --query 'PermissionSets[]' --output text); do
  [ "$(aws sso-admin describe-permission-set --instance-arn "$INSTANCE" --permission-set-arn "$p" --query PermissionSet.Name --output text)" = PricesDashboardRead ] && echo "$p"
done)
```

## 3. Once: check that Identity Center enforces MFA

Console: IAM Identity Center → Settings → Authentication → Multi-factor
authentication. This path claims "MFA enforced" only if both hold:

- users are prompted for MFA **every time they sign in**;
- a user without a registered device is **required to register one at sign-in**.

These are organization-wide settings. Do not change them for one reviewer. If
they are set differently, this path does not enforce MFA, and the M3 package
may not say it does. Use the IAM runbook instead.

## 4. Per request: the user and the assignment

Create the user in the console: IAM Identity Center → Users → Add user.
Username = the reviewer's e-mail; first name, last name, e-mail from the
request. Choose the option that sends the password-setup e-mail.

Then assign the permission set on the production account:

```bash
USERNAME=<reviewer e-mail>
USER_ID=$(aws identitystore get-user-id --identity-store-id "$STORE" \
  --alternate-identifier "{\"UniqueAttribute\":{\"AttributePath\":\"userName\",\"AttributeValue\":\"$USERNAME\"}}" \
  --query UserId --output text)
REQ=$(aws sso-admin create-account-assignment --instance-arn "$INSTANCE" \
  --target-id 750702271865 --target-type AWS_ACCOUNT \
  --permission-set-arn "$PS" --principal-type USER --principal-id "$USER_ID" \
  --query 'AccountAssignmentCreationStatus.RequestId' --output text)
aws sso-admin describe-account-assignment-creation-status --instance-arn "$INSTANCE" \
  --account-assignment-creation-request-id "$REQ" \
  --query 'AccountAssignmentCreationStatus.Status' --output text   # SUCCEEDED
```

## 5. Hand over and verify

The invitation e-mail from §4 carries the AWS access portal URL. Send the
reviewer the account (750702271865) and the role name (`PricesDashboardRead`),
then the dashboard URL:
`https://eu-central-1.console.aws.amazon.com/cloudwatch/home?region=eu-central-1#dashboards:name=prices-production-overview`

The prices operator can check the result from the production account with
`soroban-admin`:

```bash
export AWS_PROFILE=soroban-admin
ROLE=$(aws iam list-roles --path-prefix /aws-reserved/sso.amazonaws.com/ \
  --query 'Roles[?starts_with(RoleName, `AWSReservedSSO_PricesDashboardRead_`)].Arn' --output text)
echo "$ROLE"
aws iam simulate-principal-policy --policy-source-arn "$ROLE" \
  --action-names cloudwatch:GetDashboard cloudwatch:DescribeAlarms logs:GetLogEvents secretsmanager:GetSecretValue \
  --query 'EvaluationResults[].[EvalActionName,EvalDecision]' --output text
```

Expected: the two `cloudwatch:` actions `allowed`; `logs:` and
`secretsmanager:` `implicitDeny`. In a browser, as in §4 of the IAM runbook:
the dashboard renders, and the log groups page answers access denied. The
same limit applies: the explorer's dashboard `production-soroban-explorer`
opens too, because these read actions cannot be scoped per dashboard.

## 6. Remove after the review

Management account, same variables as §4:

```bash
aws sso-admin delete-account-assignment --instance-arn "$INSTANCE" \
  --target-id 750702271865 --target-type AWS_ACCOUNT \
  --permission-set-arn "$PS" --principal-type USER --principal-id "$USER_ID"
aws identitystore delete-user --identity-store-id "$STORE" --user-id "$USER_ID"
```

Then, from the production account, the `list-roles` query of §5 should print
nothing. If the role is still listed, the permission set stayed provisioned
to the account after its last assignment: ask the organization administrator
to deprovision it. Record the removal in the task history.
